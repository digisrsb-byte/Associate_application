# Phase 1 – Password Reset Security Remediation

**Branch:** `security/phase1-password-reset`  
**Status:** Implemented and tested (local UAT)  
**Date:** 2026-11-20

## Original issue

Password reset accepted **email alone** (plus new password). Anyone who knew or guessed the admin email could set a new password without proving possession of a secret.

## Root cause

`/api/auth/reset-password` authorized the change using only a matching email address. There was no single-use token, expiry, or rate limiting on reset attempts. The UI presented a one-step “reset” form that mirrored that API.

## Fix implemented

1. **Two-step flow**
   - `POST /api/auth/forgot-password` — request a reset (email only for *delivery targeting*, not authorization of the password change).
   - `POST /api/auth/reset-password` — requires **email + single-use token + new passwords**.

2. **Cryptographically secure token**
   - 32 random bytes, `base64url` encoded.
   - Stored in `auth.json` as **scrypt hash + salt** only (`passwordReset.tokenSalt` / `tokenHash` / `expiresAt`).
   - Raw token written only to local out-of-band file `data/PASSWORD_RESET_TOKEN.txt` (no SMTP in this environment).
   - Raw token is **never** returned in HTTP JSON and **never** logged.

3. **Expiry & single use**
   - TTL: **15 minutes**.
   - On successful reset: clear `passwordReset`, delete token file, clear all sessions.

4. **Rate limiting (in-memory)**
   - Forgot: max **5** requests / IP / 15 minutes.
   - Reset: max **10** attempts / IP / 15 minutes.

5. **No email enumeration**
   - Forgot always returns the same generic success message whether or not the email exists.
   - Token file is only written when the email matches the configured admin.

6. **UI**
   - Login → Forgot password (email) → Reset password (token + new password).
   - Layout/colours/branding unchanged; only the reset steps were secured.

- No ledger migration.

- Backup of test ledger was already present under `data/backups/` from prior UAT; Phase 1 does not mutate client/filing records.

## Tests performed

```bash
node scripts/phase1-password-reset-tests.mjs
```

Coverage:

- Email-only reset rejected
- Unknown email: generic response, no token file
- Known email: generic response + local token file; response does not leak token
- Wrong token → 401
- Valid token → password updated; token invalidated; file removed
- Token reuse → 401
- Login with new password; old password rejected
- Admin password restored for continued local UAT

Results: see `PHASE1_PASSWORD_RESET_TEST_RESULTS.json` (generated by the script).

## Remaining risks (deferred)

| Risk | Phase |
|------|-------|
| Client portal passwords in plaintext ledger JSON | Phase 2 |
| Server may bind beyond localhost | Phase 3 |
| Hardcoded default admin password / recovery fallbacks | Phase 4 |
| Weak PAN / text field validation | Phase 5 |
| In-memory rate limits reset on process restart | Acceptable for single-node local UAT; use Redis/shared store for hosted |
| Local token file is readable by OS users on this PC | Acceptable without SMTP; replace with email delivery for hosted |

## How to use (local)

1. Sign in screen → **Forgot password?** → enter admin email → **Send reset token**.
2. Open `data/PASSWORD_RESET_TOKEN.txt` on this machine.
3. **I already have a token** / Reset screen → paste token → new password → **Update password**.
4. Sign in with the new password.
